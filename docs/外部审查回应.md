# 外部独立审查 · 逐条回应

本文逐条回应一份外部独立审查对 ConSim 多人上限插件提出的意见。所有事实均在本地实测核对过（Cpp2IL 方法体 dump、ILSpy 反编译、实际打包体积测量），回应中保留原始路径、行号、函数名与签名，不臆造未验证内容；凡本文未验证的一律标注「未验证」。

---

## 0. 审查的核心主张与我们的一句话结论

**审查核心主张（原话要点）**：
- 大厅筛选器根因改错了地方 —— `WbUIMultiplayerLobbyFilter` 是纯本机 UI 过滤，只影响「我看别人」，不影响「别人看我」；
- 朋友的筛选器仍是原版 `filterValue = 4`；
- 只有朋友端筛选器处于激活状态时才会过滤。

**我们的结论：这条主张基本成立，审查在方向上是对的。**

我们原来的做法是去抬 `WbUIMultiplayerLobbyFilter` 里 `maxPlayerFilter` 的 `maxValue`，希望借此让 8 人房间对朋友可见。实测核对后确认：这条路径对「别人能不能看到我的房间」完全没有作用，原因见下文 (1)(3)(4)(6)；而且我们原来的实现还额外引入了一个真实副作用 bug（见 (5)），已修复。

另一方面，审查对「只抬 maxValue 毫无作用」的判断是对的，但对一个具体数字（分发体积）的估计不准，见 (9)。

## (1) PassFilter 比较的是 filterValue，不是 maxValue

**结论：审查说对了。**

**证据**：`cpp2il_ws\types\Wb.GameScripts\method_dumps\Wb\UI\WbUIFilterIntEntry_methods.txt:97-114`，方法签名：

```
System.Boolean PassFilter(System.Int32 value)
```

方法体关键指令（原文照抄）：

```
setting = this.setting;
if (setting != 1) { return 0; }
...
local4 = value <= this.filterValue;
return local4;
```

即真正的比较是 `value <= this.filterValue`，与 `maxValue` 无关。

`local5` 起的另外四段 `if (setting != N) { ... }` 分支是死码残留：Cpp2IL 把 C# 编译出来的 `switch (setting)` 跳转表渲染成了顺序的 `if/return` 序列，实际执行时永远走不到（枚举值与分支的对应关系见 (2)）。

**影响**：我们原来把 `maxValue` 抬到 8 是写在一个不影响 `PassFilter` 结果的字段上，属于无效改动。这一条我们完全接受。

---

## (2) FilterSetting 枚举与实测序列化值

**结论：审查未提到（本条是补充的实测佐证）。**

审查在核心主张里引用了「朋友的筛选器仍是原版 `filterValue = 4`」这一数值，但没有给出该数值的来源与枚举依据；我们补充如下。

**枚举定义**：`WbUIFilterIntEntry.FilterSetting`，位于 `dump.cs:859935-859943`：

| 名称 | 值 |
|---|---|
| `EQUAL_TO` | 1 |
| `LESS_THAN` | 2 |
| `GREATER_THAN` | 3 |
| `LESS_OR_EQUAL_TO` | 4 |
| `GREATER_OR_EQUAL_TO` | 5 |

**实测序列化值**（本机存档/配置实际读出的值）：

```
setting     = LESS_OR_EQUAL_TO (4)
filterValue = 4
maxValue    = 4
minValue    = 1
```

**为什么这条重要**：

1. 它解释了 (1) 里 `if (setting != 1) { return 0; }` 为什么在正常配置下是死分支 —— 实际 `setting` 是 4，不是 1；
2. 它解释了为什么「只把 `maxValue` 抬到 8」毫无作用 —— `PassFilter` 读的是 `filterValue`，玩家当前配置下 `filterValue` 就是 4，也就是「玩家数 ≤ 4 才通过」；
3. 它同时说明「把 `filterValue` 也一起改成 8」同样不该做：`filterValue` 是玩家的本机过滤条件，改它等于替朋友改他自己的筛子，语义错误（见 (5)(8)）。

## (3) 筛选器默认关闭，默认状态下不做任何过滤

**结论：审查说对了。**

**证据链**：

- `WbUIMultiplayerLobbyFilter.Awake()` 在结尾调用 `this.Deactivate()`，因此筛选器初始状态是关闭的（`isFilterActive == false`）；
- `ApplyFilterRules` 在开头判断 `isFilterActive == False` 时直接跳过后续全部分支，`maxPlayerFilter.PassFilter()` 只在 `isFilterActive == True` 那条分支内部才被调用。

**推论**：在默认（筛选器关闭）状态下，游戏根本不会调用 `PassFilter` 去过滤房间列表，8 人房间本来就该对朋友可见。因此我们原来「抬 `maxValue` 让朋友看见 8 人房间」的思路连生效的前提都不成立 —— 这是一次典型的「改了一个当前根本没被执行的条件」。

审查把这一点指出来是对的。

---

## (4) 粘性陷阱：ValueHasChanged → AnyValueChanged → Activate()

**结论：审查未提到（该机制支持审查的核心主张）。**

**机制**：

1. `WbUIMultiplayerLobbyFilter.Awake()` 把 6 个筛选项的 `ValueHasChanged` 事件全部绑定到 `AnyValueChanged()`；
2. `AnyValueChanged()` 方法体的第一句就是：

```csharp
if (isFilterActive == False) Activate();
```

也就是说，**只要任何一个筛选值发生变化，整个筛选器就会被激活**，并且是「全部条件一起生效」—— 玩家数上限、等级、ping、跨平台等过滤条件会同时参与筛选，而不是只启用被改动的那一项。

**与审查主张的关系**：审查说「只有朋友端筛选器处于激活状态时才会过滤」。这一条是对的，而本条的机制说明「激活」这件事门槛很低：不是朋友主动去开筛选器，而是他随手碰一下任何一个筛选值（哪怕是想把人数上限调大）就会把整组过滤条件打开，包括那个仍然是 4 的玩家数上限。这正好解释了为什么「我们以为朋友没开筛选器，所以什么都不用改」这个假设是危险的。

**结论**：本条我们此前没有意识到，属于审查方向提示下我们补做核对才发现的机制；记录在此，作为 (5) 的前提。

---

## (5) 我们原实现里的 ValueHasChanged.Invoke() 是真实 bug

**结论：审查说对了。**

**问题**：我们原先的 `BoostLobbyFilter`（`plugin\ConSimMorePlayers\Patches.cs:379-429`）在改写筛选项的显示值之后，调用了：

```csharp
entry.ValueHasChanged.Invoke();
```

结合 (4) 的机制可知，这行调用的实际效果是：**在看大厅列表的那一侧强行把筛选器激活**。`BoostLobbyFilter` 是跑在本机的补丁，作用对象就是「正在看大厅的那个人」的筛选器（在审查的语境里就是「朋友端」）；而这一侧的 `filterValue` 仍然是原版的 4，一旦整个筛选器被激活，玩家数上限过滤立即开始生效，结果是「原本能看见的房间反而被过滤掉了」—— 我们把一个可见性问题改成了更严重的可见性问题。

这与审查的判断一致：改的地方不对，而且改法本身引入了副作用。

**修复**：

- 删除该 `entry.ValueHasChanged.Invoke()` 调用；
- 只写显示文本 / 只写 `maxValue`，绝不触发事件、绝不覆写 `filterValue`；
- 大厅列表刷新交给游戏自身的 `_UpdateRoomList` 协程负责，不做任何主动刷新。

**当前代码状态**：`Patches.cs:379-429` 内已带长注释说明「绝不 Invoke ValueHasChanged」，实现为 write-only（只抬 `maxValue` 与 `filterValue` 的显示侧，不派发事件）。相关约束在 `Patches.cs:333-355` 的 `Prefix_EnsureMaxRaised` 上也有注释：「只动 maxValue，绝不覆写 filterValue —— 覆写会让玩家怎么点都弹回原值」。

## (6) 房间容量真正由 RoomOptions.MaxPlayers 决定

**结论：审查说对了。**

审查主张「根因改错了地方」，即真正决定「房间里能进几个人」的不是大厅筛选器。核对结果支持这一判断。

**容量链路（建房侧）**：

```
WbRoomData.maxPlayers
  → _CreateRoomCoroutine 用它循环生成 RPPlayerInfo%02d 玩家属性槽位
    → RoomOptions.MaxPlayers
      → PhotonNetwork.CreateRoom
```

这条链路上所有环节都由**同一个 int** 派生，因此在源头改一处即可整体放大，不需要分别改每个环节。

**关键佐证**：`InitializeRoomProperties(WbRoomData)` 只写入以下字段：

- `levelSetting`
- `companyLevel`
- `hostPlayerLevel`
- `hostCharacterID`
- `minLevel`
- `passwordRequired`
- `ping`
- `crossplayEnabled`

**不包含 `maxPlayers`**。因此容量完全由 `RoomOptions.MaxPlayers` 决定，不存在「房间自定义属性里的 maxPlayers」这种可改的东西（这一点是我们在核对时特意排除的：如果容量在房间属性里，理论上可以服务端下发，实际上不是）。

**结论**：审查指出应把注意力放在 Photon 房间容量层而不是大厅 UI 过滤层，方向正确。

## (7) 原版建房 UI 门禁：hasFinishedStartCampaign

**结论：审查未提到。**

**事实**：原版 `SetupMPCreationCard()` 中有：

```csharp
createMultiplayerGameButton.interactable = metaData.hasFinishedStartCampaign;
```

也就是**必须过完新手教程，多人建房的按钮才会变为可点击**。

**记录原因**：这类「原版门禁」在排查「为什么建房按钮是灰的」时很容易被误判成插件问题（我们自己的构建过程中就出现过对按钮状态的怀疑）。它与本次审查焦点无关，但属于必须写下来避免后人重复踩坑的事实，故一并列出。

---

## (8) 原版 IncreaseValue / DecreaseValue 逻辑本身正常

**结论：审查未提到。**

**事实**：`WbUISettingEntryInteger.IncreaseValue` / `DecreaseValue` 的原版实现逻辑是正常的：

- 每次 ±1；
- 越界时夹紧（不会越出 `minValue` / `maxValue`）；
- 修改后正确刷新显示文本与两侧按钮的可用状态。

**曾经的「箭头点不动」不是原版 bug，而是我们自己的补丁造成的**：我们的补丁在每次点击后都把 `filterValue` 强写回目标值，玩家的点击刚把值改掉就被立刻覆写回去，表现为「点了没反应 / 弹回原值」。

**当前状态**：已修。现在只抬 `maxValue`，绝不覆写 `filterValue`。

**为什么这条要写进回应**：审查如果只看到「筛选值改不动」的现象，很容易把它归因到原版缺陷上；实际根因在我们这边，且已修复。把它单列出来，避免后续复查时再次误判。

## (9) 分发体积：「解压后 160 MB+」这个说法不准确

**结论：审查说错了。**

**实测数据**（本机 `Get-ChildItem -Recurse | Measure-Object Length -Sum`）：

| 项目 | 字节数 | 约合 |
|---|---|---|
| 一键包目录总计（`一键包\` 递归） | 34,395,680 | 32.8 MB |
| 分发用 zip（`ConSim-多人解锁-一键安装包.zip`） | 34,170,586 | 32.59 MB |
| `payload\BepInEx6-win-x64.zip` | 34,336,405 | ≈32.7 MB |
| `payload\ConSimMorePlayers.dll` | 15,872 | ≈15.5 KB |
| BepInEx6 解压后（`tools\BepInEx6\unpacked` 递归） | 75,667,532 | 72.16 MB |

**事实说明**：

- 一键包分发体积是 **32.59 MB**；
- BepInEx6 的 zip **不包含游戏的 interop 程序集**，interop 是首次运行时在本地生成的（解压后目录中确实不存在任何 interop 目录，已实测确认）；
- 解压后约 32.8 MB，安装进游戏目录后约 72 MB（仍不含 interop）。

**审查的 160 MB+ 从哪来**：那更像是**含 interop 的安装后体积**（即游戏跑过一次、interop 已生成之后），而不是「解压后」的体积。作为「解压后」的估计，它高了一倍以上，所以说错了 / 不准确。

**这一点对分发的实际影响**：不影响功能，但会影响朋友的预期（例如有人会以为要下 160 MB 而放弃）。分发时以 32.59 MB 为准。
