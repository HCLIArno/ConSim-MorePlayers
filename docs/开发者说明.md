# ConSim More Players —— 开发者说明

Construction Simulator（IL2CPP / BepInEx 6）的多人房间人数上限解锁插件。本文件面向**改这个插件的人**，记录工程结构、构建流程，以及开发期踩过的坑。面向拿到安装包的普通朋友的说明在 [`一键包/说明.txt`](一键包/说明.txt)；对外部审查的逐条回应在 [`外部审查回应.md`](外部审查回应.md)。

## 2. 【最重要的坑】必须显式 Register 每个补丁

**不要在 `Patches` 类里用 `[HarmonyPatch]` 特性 + `harmony.PatchAll(typeof(Patches))`。**

实测结论（已写在 [`Patches.cs:27-31`](plugin/ConSimMorePlayers/Patches.cs#L27-L31) 的注释里）：

> 不用 `harmony.PatchAll(typeof(Patches))`：实测在 BepInEx 6 / HarmonyX 下它没有处理嵌套类里的 `[HarmonyPatch]`，也没有报错，导致全部补丁静默失效。

具体的危害在于**它不报错**：

- 游戏正常启动，插件正常加载，`LogOutput.log` 里能看到「已加载」；
- 但一个补丁都没挂上，界面行为完全是原版；
- 因为没有任何异常，排查时很容易往「逻辑写错了」「方法名找错了」方向查，实际上根因是「补丁压根没被注册」。

**本工程的做法**：在 [`Patches.cs:32-90`](plugin/ConSimMorePlayers/Patches.cs#L32-L90) 的 `Initialize(Harmony harmony)` 里，对每个补丁逐条调用 `Register(...)`，用 `AccessTools.Method(typeof(T), "方法名")` 显式解析目标方法。`Register`（[`Patches.cs:92-127`](plugin/ConSimMorePlayers/Patches.cs#L92-L127)）负责：

1. `target == null` → 打 `[注册失败] <label>：找不到目标方法`；
2. prefix / postfix 方法名解析不到 → 打 `[注册失败] <label>：找不到补丁方法 <name>`；
3. 成功 → 打 `[注册成功] <label>`；
4. `harmony.Patch(...)` 抛异常 → 打 `[注册失败] <label>：<异常>`。

调用点在 [`Plugin.cs:83-90`](plugin/ConSimMorePlayers/Plugin.cs#L83-L90)，外面包了 try/catch，失败会打 `补丁注册失败: <异常>`。

**新增补丁时的规矩**：在 `Initialize` 里加一条 `Register`，`label` 写成「目标类型.方法名」，prefix/postfix 用 `AccessTools.Method(typeof(Patches), "方法名")` 解析。**不要**给补丁方法加 `[HarmonyPatch]` 特性指望自动发现 —— 在这套环境里它不工作。

### 3.3 csproj 的关键约定

- `TargetFramework` = `net6.0`（BepInEx 6 的 IL2CPP 运行时就是这个目标）；
- `AppendTargetFrameworkToOutputPath` = `false` → 产物直接落在 `bin\Release\`，不是 `bin\Release\net6.0\`；
- `AssemblyName` = `ConSimMorePlayers`，`Version` = `1.0.0`；
- **所有游戏侧的引用 `Private` 都是 `false`**，即不复制到输出目录。这一点是必须的：`BepInEx.Core` / `0Harmony` / 各 `Wb.*` interop 程序集在游戏目录里已经有一份，跟着 DLL 一起发出去只会造成版本冲突。

引用路径全部来自游戏安装目录（`GameDir` = `D:\Software\steam\steamapps\common\Construction Simulator`）：

| 属性 | 实际路径 |
|---|---|
| `BepInExCore` | `$(GameDir)\BepInEx\core` |
| `InteropDir` | `$(GameDir)\BepInEx\interop` |
| `UnityLibs` | `$(GameDir)\BepInEx\unity-libs` |

**因此：插件必须在「已经跑过一次游戏、interop 已生成」的机器上编译。** interop 程序集不是随包分发的，是 BepInEx 首次运行时在本地生成的（见 `外部审查回应.md` 第 (9) 条）。换机器编译前先让游戏跑起来一次，否则 `Wb.GameScripts` 等引用全部解析不到。

## 4. 怎么断言「补丁真的生效了」

**唯一可信的依据是 `LogOutput.log`，不要凭界面推断。**

日志路径：

```
<游戏目录>\BepInEx\LogOutput.log
```

启动游戏后在这个文件里搜三类行：

| 行 | 含义 | 由谁打 |
|---|---|---|
| `ConSim More Players 已加载，目标房间人数 = N，解锁联机建房 = False` | 插件被 BepInEx 加载了、Config 读到了 | `Plugin.cs:80-81` |
| `[注册成功] <label>` | 该补丁**挂上了** | `Patches.cs:121` |
| `[注册失败] <label>：<原因>` | 该补丁**没挂上**，原因写在冒号后 | `Patches.cs:99 / 112 / 125` |
| `[补丁生效] <name>` | 该补丁的方法**至少被执行过一次** | `Patches.cs:24`（`MarkFired`） |
| `补丁注册失败: <异常>` | `Patches.Initialize` 整体抛异常 | `Plugin.cs:89` |

**为什么不能凭界面推断**：界面行为受太多因素影响（配置为默认值、原版门禁没通过、玩家没操作到那条路径）。「界面看起来对」不能证明补丁挂上了，「界面看起来不对」也不能证明补丁没挂上 —— 这两件事本项目都遇到过。

**怎么让 `[补丁生效]` 有意义**：`MarkFired`（[`Patches.cs:17-25`](plugin/ConSimMorePlayers/Patches.cs#L17-L25)）内部有一个 `Fired` HashSet 去重，**每个补丁名只打一次**。所以：

- `[注册成功]` 全都在、但某条 `[补丁生效]` 缺失 → 说明这个补丁挂上了但触发时机没走到（比如玩家没打开对应界面），不是注册失败；
- 一条 `[注册成功]` 都没有 → 回到第 2 节，先怀疑注册表本身。

### 4.1 日志的一个坑：不要用 `Console.WriteLine`

必须走 BepInEx 的 `ManualLogSource`。`Console.WriteLine` 在 `redirect_output_log=false` 时**不会进日志文件**。见 [`Plugin.cs:42`](plugin/ConSimMorePlayers/Plugin.cs#L42) 的注释。

本工程的日志出口在 [`Plugin.cs:43-53`](plugin/ConSimMorePlayers/Plugin.cs#L43-L53)：

- `LogInfo(msg)` —— 受 `VerboseLog` 配置项控制，常规信息用它；
- `LogAlways(msg)` —— **绕过** `Verbose` 开关，用于「补丁是否生效」这类必须看到的诊断。

`[注册成功]` / `[注册失败]` / `[补丁生效]` / `[补丁注册失败]` 全部走 `LogAlways`，所以即使玩家把 `VerboseLog` 关掉，注册诊断依然在日志里。

### 4.2 配置项

`BepInEx\config\com.dsh.consim.moreplayers.cfg`（由 `Config.Bind` 生成，[`Plugin.cs:59-76`](plugin/ConSimMorePlayers/Plugin.cs#L59-L76)）：

| 键 | 默认 | 说明 |
|---|---|---|
| `General.MaxPlayers` | `8` | 房间最大玩家数（原版 4）。`Target` getter 夹紧到 `1..32`（`HardCap`）。 |
| `General.VerboseLog` | `true` | 关掉后只保留 `LogAlways` 的行。 |
| `General.UnlockMultiplayer` | `false` | 绕过「必须先通关开局战役」的门禁。默认保持原版行为。 |

插件自己的 `Plugin.Target` 是唯一的人数出口，所有补丁都读它，不要在补丁里另算一份。

## 5. 其他踩过的坑

### 5.1 `dump.cs` 有签名不等于看懂了行为

原版 `WbUIFilterIntEntry.PassFilter` 的比较对象是 `filterValue` 而不是 `maxValue`：

- 方法体证据：`cpp2il_ws\types\Wb.GameScripts\method_dumps\Wb\UI\WbUIFilterIntEntry_methods.txt:97-114`；
- 方法体里 `local5`..`local8` 四段是 Cpp2IL 把 `switch (setting)` 渲染成顺序 `if/return` 的**死码残留**，不要照着它们推逻辑。

只读 `dump.cs` 的字段列表（`filterValue` / `maxValue` 都在）会得出「抬 maxValue 就能改过滤结果」的错误结论。**改任何条件判断之前，先看方法体。**

### 5.2 `ValueHasChanged` 是陷阱，不要 Invoke

`WbUIMultiplayerLobbyFilter.Awake()` 把 6 个筛选项的 `ValueHasChanged` 全绑到 `AnyValueChanged()`，而 `AnyValueChanged()` 第一句是：

```csharp
if (isFilterActive == False) Activate();
```

即**任何**筛选值变化都会把整个筛选器激活（连带等级 / ping / 跨平台等条件一起生效）。我们原实现在改写值之后调了一次 `entry.ValueHasChanged.Invoke()`，等于在玩家端强行打开筛选器，会把原本可见的房间过滤掉。

现在 [`Patches.cs:379-429`](plugin/ConSimMorePlayers/Patches.cs#L379-L429) 的 `BoostLobbyFilter` 是 write-only，注释里写死了「绝对不要 Invoke() 这个事件」。**改这段代码之前先读那段注释。**

### 5.3 不要覆写 `filterValue`

玩家用箭头调的当前值存在 `filterValue` 里。覆写它会让玩家「怎么点都弹回原值」（点一下、我们的补丁写回去、看起来像箭头坏了）。正确做法是只抬 `maxValue`（抬高天花板），让原版的 `IncreaseValue` / `DecreaseValue` 正常夹紧。

- `Prefix_EnsureMaxRaised`（[`Patches.cs:331-355`](plugin/ConSimMorePlayers/Patches.cs#L331-L355)）：只动 `maxValue`；
- 认「哪个才是最大玩家数控件」**不要用数值猜**（曾经用 `minValue == 2` 猜，改版就失效，还可能误伤别的设置项）。现在是在 `ShowScreenContent` 时把 `screen.maxPlayerSetting` 的真实引用缓存进 `_maxPlayerSetting`，之后用 `ReferenceEquals` 精确认人（[`Patches.cs:323-347`](plugin/ConSimMorePlayers/Patches.cs#L323-L347)）。

### 5.4 改字段不会自动刷新 UI

`WbUISettingEntryInteger` 改 `filterValue` / `maxValue` 之后界面不会自己更新 —— 原版是在 `IncreaseValue` / `DecreaseValue` 里手动更新文本与箭头按钮状态的。所以我们照抄了那条路径，见 `RefreshSettingUI`（[`Patches.cs:298-321`](plugin/ConSimMorePlayers/Patches.cs#L298-L321)）：更新 `settingValue.text`（`ToString("00")`）与两侧 `SetInteractable`。

### 5.5 原版门禁：`hasFinishedStartCampaign`

`SetupMPCreationCard()` 里有 `createMultiplayerGameButton.interactable = metaData.hasFinishedStartCampaign;` —— 没过完新手教程就没法建房。排查「按钮为什么是灰的」时先想这条，不要先怀疑插件。

### 5.6 房间容量的真正链路

```
WbRoomData.maxPlayers
  → _CreateRoomCoroutine 用它循环生成 RPPlayerInfo%02d 玩家属性槽位
    → RoomOptions.MaxPlayers
      → PhotonNetwork.CreateRoom
```

同一个 int 派生，源头改一处即可。`InitializeRoomProperties(WbRoomData)` **不含** `maxPlayers`，所以容量不在房间自定义属性里，改那里没用。`RoomOptions.MaxPlayers` 是 byte（见 [`Plugin.cs:23`](plugin/ConSimMorePlayers/Plugin.cs#L23) 注释），`HardCap = 32` 就是按这个来的。

### 5.7 大厅筛选器是纯本机 UI 过滤

`WbUIMultiplayerLobbyFilter` 只影响「我看到的房间列表」，**不影响别人是否看到我的房间**。而且它默认是关闭的（`Awake()` 结尾 `Deactivate()`），关闭状态下 `ApplyFilterRules` 直接跳过全部 `PassFilter` 检查。

**结论：想靠改本机筛选器让别人看到自己的 8 人房间，方向是错的。** 详见 [`外部审查回应.md`](外部审查回应.md)。

## 7. 改代码时的红线

1. **不要改** `一键包\payload\` 里的文件（那是分发产物，改了要重新打包并说明）；
2. **不要改** `一键包\说明.txt` 的编码 —— 它必须是 **UTF-8 带 BOM**（前 3 字节 `EF BB BF`）。用编辑器保存时注意别把 BOM 丢了（PowerShell 的 `Set-Content -Encoding UTF8` 行为随版本变化，稳妥做法是 `New-Object System.Text.UTF8Encoding($true)` + `[System.IO.File]::WriteAllText`）；
3. **不要给补丁方法加 `[HarmonyPatch]` 特性**（见第 2 节）；
4. **不要在补丁里 Invoke `ValueHasChanged`**（见 5.2）；
5. **不要覆写 `filterValue`**（见 5.3）；
6. 新增/修改补丁后，**必须**在 `LogOutput.log` 里确认对应的 `[注册成功]` 行，光看界面不算验证。
